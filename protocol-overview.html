How the lending market works

Suppliers fund a shared pool of base tokens. Borrowers lock collateral and draw from that pool. Two global indices track interest, while an oracle and collateral factor determine borrowing power.

The key mental model: the proxy holds the tokens and account state; LendingMarket supplies the logic. Supply balances, debt balances and available cash are separate quantities.

The basic design is small and readable. Several implementation details materially affect its behavior, especially liquidation pricing, principal rounding, oracle handling and guardian permissions. This report describes the actual code and identifies where it diverges from the documented design.

Architecture and custody

Each market instance is configured with one ERC20 base token, one ERC20 collateral token and one price oracle. The staging helper uses bUSD as the base and WETH as collateral. There is no multi-asset portfolio engine, share-token contract or separate vault in this implementation.

Execution layer

Users call the proxy address. Its fallback delegates to LendingMarket, preserving the caller and using the proxy’s storage. Upgrades replace the logic address without moving balances or tokens.

State layer

Per-account mappings record supply principal, borrow principal and collateral. Global totals and indices allow balances to grow without updating every account. Supplier claims are internal records and have no transfer function.

Protocol inputs and outputs

Users supply token amounts in raw ERC20 units and approve the proxy address for incoming transfers. With the staging assets, 1e18 raw units means one token. User mutation functions return no Solidity value; their outputs are token transfers, changed storage and events. A reverting call rolls back its effects.

All token-amount actions require a positive input. Ordinary supply, withdrawal, borrowing and repayment act on msg.sender; there is no “on behalf of” argument. Liquidation reduces another account’s debt.

Other external inputs

The oracle supplies a signed price answer; block.timestamp supplies elapsed time. Initialization supplies five addresses and three risk/rate values. Administrators can subsequently change the oracle, collateral factor, incentive, borrowing rate and pause state; the proxy admin can change implementation code.

Read outputs

supplyBalanceOf(account) and borrowBalanceOf(account) return raw base amounts. isHealthy(account) returns a boolean. getPrice() and utilization() return values expected to use 1e18 scaling. Public getters expose principal, collateral, totals, indices, addresses and parameters. These balance/health views use the last stored indices, so they exclude interest since the last accrual.

Accounting and interest

Let F = 1e18. Principal is a normalized bookkeeping balance. The index converts it into the current token-denominated claim or debt. Both indices start at F.

Supply balance = floor(supply principal × supply index / F) Borrow balance = floor(borrow principal × borrow index / F) Principal for an amount = floor(amount × F / relevant index)

For example, 1,000 principal units at a supply index of 1.05 represent a 1,050-base claim, before integer rounding. This is how account balances grow while the account’s principal remains unchanged.

How an accrual advances the indices

The borrowing rate is fixed by the admin. Utilization is reported as a view but does not set that rate. For one accrual interval, the code reads total debt B and total supply claims S using the old indices:

Δt = current timestamp − last accrual timestamp i = rate per second × Δt [1e18 scaled] New borrow index = old borrow index + floor(old borrow index × i / F) A = floor(B × i / F) [interest allocated to suppliers] If S > 0: New supply index = old supply index + floor(old supply index × A / S)

Interest is linear within an interval and compounds across successive accruals. With a 5% annualized rate, 100,000 base of debt and 1,000,000 base of supply claims, a single year-long interval adds roughly 5,000 to debt and to aggregate supplier claims: roughly 0.5% supplier return at 10% starting utilization. Rounding and call timing affect exact results.

Claims versus cash

Accrual moves no tokens. Supplier interest is a claim on future borrower repayments. Borrowing reduces pool cash; repayment replenishes it. A supplier can hold a valid claim yet be unable to withdraw while the pool lacks base tokens.

No reserve or loss mechanism

The formula allocates accounted borrower interest to suppliers with no reserve fee. Collateral earns no interest here. There is no explicit reserve balance, bad-debt write-off or supplier loss-allocation path.

utilization = floor(total debt × F / total supply claims), or zero if supply claims are zero. It is not capped at 100%. The borrow index advances even when debt is zero; the supply index advances only when supply claims are positive.

Borrowing power and liquidation

Collateral value = floor(collateral balance × oracle price / F) Borrowing power = floor(collateral value × collateral factor / F) Healthy = borrowing power ≥ stored-index debt

Ten WETH at 2,000 base each, with an 80% factor, gives 16,000 base of borrowing power. Borrowing 15,000 leaves a 1,000-base margin. At a price of 1,800, borrowing power falls to 14,400, making the same debt liquidatable. Equality is healthy. Debt-free accounts return healthy without an oracle query.

The same collateral factor controls borrowing eligibility and liquidation eligibility; there is no separate liquidation threshold. Anyone can liquidate an unhealthy borrower. There is no close factor limiting a repayment fraction and no requirement that the remaining position become healthy.

The implemented seizure omits the price

The code computes seized = min(collateral balance, floor(repaid base × incentive / F)). It does not convert the base value to collateral using the oracle price.

In the existing liquidation test, 1,000 bUSD repaid at a 110% incentive calculates 1,100 WETH before the cap, so all 10 WETH are seized. A price-based conversion at 1,800 bUSD/WETH would produce approximately 0.6111 WETH. That comparison describes the economic formula implied by the documentation; it is not the formula executed by this contract.

At the test’s unchanged indices, this leaves 14,000 bUSD of debt and zero collateral. The cap does not lower repayment, and the code has no mechanism to resolve the remaining unsecured debt.

Critical design points

These are source-level observations relevant to understanding the protocol. The eight current tests do not exercise most of these boundaries; this report is an architecture review, not a complete exploit assessment.

Principal rounding

Every amount-to-principal conversion rounds down, including borrow and withdrawal. At an index above 1e18, a positive one-raw-unit amount can convert to zero principal: tokens may leave while no claim is debited or debt recorded. Some full-balance repayments can leave residual principal. Direction-specific rounding and minimum-principal handling are important missing boundaries.

LendingMarket.sol:332–340; 169–239

Debt freshness

withdrawCollateral() checks health without first accruing interest. It can therefore approve a withdrawal against debt that excludes elapsed interest. Read-only health and balance calls also use stored indices; callers need to distinguish those values from debt after an accrual.

LendingMarket.sol:199–206; 286–319

Oracle and units

The market reads only the price answer and casts it to uint256. It checks neither positivity nor freshness nor round completeness. Negative answers become large unsigned values, potentially distorting valuations or causing arithmetic reverts. Token/feed decimals() are not consulted; the shown economics assume 18-decimal assets and a 1e18-scaled price. A raw feed with different scaling is not automatically compatible.

LendingMarket.sol:323–325; interfaces/IPriceOracle.sol; interfaces/IERC20.sol

Token integration

ERC20 transfer return booleans are ignored. A false-returning token can leave accounting updated without payment. Incoming transfer amounts are not verified through balance deltas, so transfer fees also break the assumed accounting. There is no reentrancy guard; token behavior is part of the trust boundary. The included mocks return true and have ordinary transfers.

LendingMarket.sol:160, 179, 191, 208, 223, 237; 276–277

Liquidity and insolvency

There is no explicit cash-availability check; outgoing transfers rely on token behavior, and the provided mock reverts when balances are insufficient. There are no supply/borrow caps or explicit minimum positions. Capped collateral seizure can leave unsecured debt, while supplier claims remain recorded without an explicit loss-resolution path.

LendingMarket.sol:169–226; 261–277

Emergency control

Pausing blocks supply, withdrawal, collateral deposit/withdrawal, borrowing and liquidation. Repayment and interest accrual remain available. That means a pause also blocks supplier exits, adding collateral to improve health and liquidation of risky accounts. The guardian can unpause and replace the oracle, extending beyond the stop-only role described in the README.

Two different admin records: setAdmin() changes the market’s admin variable, but leaves the proxy-admin slot unchanged. The former market admin can retain upgrade control after market administration is transferred.

Proxy behavior: despite its name and comment, the fallback delegates calls from every sender, including the proxy admin. Explicit proxy functions intercept their own selectors. Native ETH can be received, but has no corresponding lending or withdrawal accounting.

Initialization is once-only per storage context but performs no address or risk-parameter validation. The staging constructor initializes the proxy atomically. The implementation is not separately initializer-locked. The hardcoded addresses in the helper do not themselves establish the timelock/multisig governance described in the README.

Appended: the lending market test contract

LendingMarketTest in test/LendingMarket.t.sol is a Foundry integration-style suite. It exercises market calls through the actual proxy with mock tokens and a mock oracle. It contains eight deterministic tests, focused mostly on normal user flows plus one borrowing-limit rejection.

Where and how it tests

setUp() deploys 18-decimal bUSD and WETH mocks, a 2,000-base oracle, the implementation and an initialized proxy. It uses the staging market’s 80% factor, 110% incentive and roughly 5% borrowing rate, then mints and supplies 1,000,000 bUSD to seed liquidity. Helpers mint/approve borrower collateral; Foundry impersonation selects actors, and vm.warp() advances time for interest testing. This is a local Solidity environment, with no live-chain fork or real token/feed integration.

Main areas outside current coverage

  • Accounting boundaries: exact borrower/supplier interest, multiple accrual intervals, tiny principal conversions, full repayment after interest and aggregate accounting consistency.
  • Collateral and liquidation: collateral withdrawal with accrued debt, expected price-based seizure, seizure caps and residual unsecured debt.
  • External dependencies: stale/zero/negative oracle answers, feed/token decimals, insufficient cash, false-returning or fee-charging tokens and reentrancy behavior.
  • Roles and lifecycle: unauthorized calls, guardian oracle/unpause powers, pause enforcement, admin transfer, initialization validation/reinitialization and state preservation across upgrades.

foundry.toml configures 256 fuzz runs and invariant runs of 64 with depth 32. This suite has no parameterized fuzz tests or invariant functions, so those settings do not add those forms of coverage. In particular, the liquidation test’s “received > 0” assertion allows the excessive seizure described above to pass.
